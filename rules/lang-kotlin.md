# Kotlin / JVM Rules

Applies to Kotlin, and to the JVM stack it runs on (Spring, JPA/Hibernate, Gradle). Language-agnostic style lives in `preferences.md`; query and schema rules live in `lang-sql.md`. Defaults yield per the precedence ladder in `CLAUDE.md`.

## Kotlin idioms
- Prefer named variables and early returns over chained scope/lambda helpers that do not earn their keep.
- Prefer a plain `if` over a ternary or elvis chain, and an early `return` over assigning an if/else expression to a variable. A `var` plus an `if` is fine; do not "simplify" it away.
- Never assign a `try`/`catch` or an `if`/`else` block to a variable, however Kotlin lets you. Declare the variable with its explicit type on its own line, assign inside the block, and `return`/`throw` from the failing branch — the value's type stays visible and the happy path reads top to bottom. This holds even when the block is a single expression.
- A collection property defaults to empty, never null — `List<X> = emptyList()`, not `List<X>? = null`. A nullable collection pushes a null check onto every caller to express nothing.
- If a property carries `@NotNull`, its type is non-nullable. Declaring it nullable and annotating it means the null is rejected at the edge and still treated as possible everywhere after.
- Every `!!` must name the constraint or guard that makes it safe. If you cannot name one, write `?: throw` with a message — the message reaches the log and the caller, the `!!` reaches neither.
- Validation annotations on a constructor property need the `@field:` use-site target. A bare `@NotNull`/`@Size` binds to the constructor parameter, where no validator ever reads it, so the constraint compiles, looks present in review, and never runs.
- Compare `Duration`s or millis, never `toHours()`/`toMinutes()` — those truncate, so 12.9 hours passes a 12-hour cap. For a date-only comparison truncate both sides explicitly; a persisted datetime keeps its time component.
- Stamp with `Instant`, and put the zone in the name of any field or parameter carrying wall-clock time (`firstRunAtUtc`, not `firstRunAt`). A hardcoded zone inside a service that serves more than one country is a bug waiting for the second country.

## Spring
- Fire-and-forget background work must never throw; catch and log only. A job that declares `retries > 0` is not fire-and-forget — catching there silently disables every retry, so either rethrow or set `retries = 0` and mean it. A guard that *skips* work is a third case: log and return, without burning a retry.
- Reach another component through its service, never its repository. A repository is for its own component only; when you need someone else's data, call their service and add a thin delegating method there if none fits. Never inject both a service and its own repository into the same class — that is redundant by definition, so route the reads through the service and drop the repository injection. This applies to injections an earlier change deliberately left alone: once a service injection into that component exists for any reason, the "avoid a second edge" argument that justified the repository is spent, and consolidating removes an edge rather than adding one. Watch for a delegating method landing inside a caller that already sets thread-local or transactional state — if the framework's annotation nests badly (a read-replica or propagation marker that resets the outer scope), leave the new method bare.
- Every controller's class-level `@RequestMapping` carries the whole shared base path its routes have in common — including the resource/component segment, not just a common prefix that leaves the resource on each method. A method mapping then names only what varies. Splitting the resource segment out to the class base reads at a glance; apply it to all API controllers, and match whichever split the nearest sibling uses rather than inventing a third. This never changes the resolved URL — it only moves where the constant path lives — so it stays an additive, zero-behaviour-change edit.

## JPA / Hibernate
- Never put a repository call or a remote API call inside a loop. One query per row is the same defect whether the loop is in the service or generated by the ORM — batch it into a single call keyed on the ids.
- Push the predicate into the query. A `findAll…` followed by an in-memory `.filter {}` loads every row to discard most of them; add the derived finder that filters in SQL, and use `exists`/`count` when you only need the answer.
- Never load whole rows for data you immediately discard. If a step needs only ids, one column, or a count, write a projection query that selects exactly that. Loading full entities to keep a single field also drags in every EAGER association, so one call becomes one query per row unless a batch-fetch size is configured — read the entity's associations before assuming a finder costs one query. Add the projection as a new method beside the existing finder and leave that finder untouched for the callers that genuinely need the whole row.
- On a read path, don't dereference a LAZY association just to map one or two of its fields. With OSIV off, that access forces the method to hold a session open, so it needs `@Transactional` solely to keep the proxy alive — a transaction that exists for nothing else. Prefer fetching those fields with a separate scalar/id-keyed finder (within the component; another component's data still goes through its service): it returns them with no session and no transaction, and when the added query count is a fixed handful — a single-row lookup by PK or an indexed key — the extra round trip is negligible. The trade never overrides the no-repo-call-in-a-loop rule: for a collection, fetch-join or project instead, never one query per row.
- Deleting or updating a known set of rows is one statement, not one per row. Prefer a bulk/batch call keyed on `IN (ids)` over iterating; where the ORM offers both an entity-collection and an id-collection batch form, take the id form — the entity form usually expands to an `OR` chain that grows a clause per row. Before switching, confirm nothing depends on per-row lifecycle callbacks or cascades, since bulk statements bypass them.

## Build
- A JVM build daemon that dies with OOM corrupts the incremental cache, so the retry fails with a different, misleading error. Stop the daemon, delete the build cache directory, raise the heap, then rebuild.
